HOW TO RUN AUDITS LOCALLY
================================================================================

SETUP (first time only)
------------------------
cd ~/Documents/assembly_code/website_audit_tool
source venv/bin/activate
cd gtm_verifier


TWO MODES
---------
1) FOREIGN SITE (prospect / cold audit) — no config file needed at all:
     python run.py --url https://prospect.com
   Runs the six site-agnostic audits: analytics_audit, consent_audit,
   network_audit, tag_inventory, seo, security_headers.

2) CLIENT SITE (we're under the hood) — YAML config with journeys:
     python run.py                          # config.yaml (Palm View test ground)
     python run.py --config client.yaml     # a specific client
   Runs the six audits PLUS every journey defined in the config's
   journeys: section, and verifies the expected GTM/GA4 IDs are live.

Useful flags:
  python run.py --list                     # show available audits + configured journeys
  python run.py shop cart                  # run specific audits/journeys only
  python run.py --export report.pptx       # PowerPoint instead of terminal
  python run.py --url https://staging.client.com --config client.yaml
                                           # client journeys against another env
  HEADLESS=1 python run.py ...             # no visible Chrome window


ONBOARDING A NEW CLIENT (no code changes, ever)
-----------------------------------------------
1. cp config.example.yaml client.yaml
2. Set site.base_url and (if known) tags.gtm_id / tags.ga4_id.
3. Set selectors.consent.accept_button only if the common-CMP auto-detection
   misses their banner.
4. Write journeys: for the flows that matter. Each journey is steps
   (goto / click / type / select_index / accept_consent / mark) plus
   expect blocks naming the dataLayer event, required fields
   (dot-notation), and optional regex patterns.
   Selector how-to: DevTools -> right-click element -> Copy -> Copy selector.
5. python run.py --config client.yaml

The full step/expect schema is documented in config.example.yaml and at the
top of journeys.py. palm_view_config.yaml is a complete worked example.


WEB FRONT END
-------------
flask --app webapp.app run          (from gtm_verifier/, HEADLESS=1 optional)
Open http://localhost:5000. Enter a URL for the public/authorized audits;
upload a client config YAML to also run its journeys and verify tag IDs.


DEPLOYED WEB APP (Cloud Run)
----------------------------
The web front end also runs in GCP, so the team can audit without a local venv:
project project-atlas-audit, region europe-west2, service gtm-verifier.
It sits behind IAP — sign in with a Google account that has been granted
roles/iap.httpsResourceAccessor.

Ship a new revision (Cloud Build builds the Dockerfile; no local Docker needed):
  ./deploy.sh

Tail logs:
  gcloud run services logs read gtm-verifier \
      --project project-atlas-audit --region europe-west2

FIRST-TIME GCP SETUP (once per machine)
  gcloud auth login fela@cloud-runner.co.uk
  gcloud config set account fela@cloud-runner.co.uk
  gcloud config set project project-atlas-audit
  gcloud services enable run.googleapis.com cloudbuild.googleapis.com \
                         artifactregistry.googleapis.com iap.googleapis.com

FIRST-TIME IAP SETUP (already done for this project)
  Cloud Run's integrated IAP supplies its own Google-managed OAuth client, so
  there is NO OAuth consent screen to configure in the console — enabling it is
  the whole step:
     gcloud beta run services update gtm-verifier \
         --project project-atlas-audit --region europe-west2 --iap
  It also needs cloudresourcemanager.googleapis.com enabled for the IAM calls
  below to work.

ADDING A USER
     ./iap_access.sh add someone@example.com [more@example.com ...]
     ./iap_access.sh list
     ./iap_access.sh remove someone@example.com

  Access is an explicit per-user allowlist, and it is IAM — signing in with
  Google is not enough, the account also needs the binding. Any domain works;
  the org has no domain-restricted-sharing policy. Changes take up to a minute,
  and an already-signed-in user may need a hard reload to clear the old verdict.

  Once the list grows past a handful, make a Google Group and bind it once
  instead of maintaining individual bindings:
     ./iap_access.sh add group:audit-team@cloud-runner.co.uk

  Anyone with access can drive a real browser at any URL from inside GCP —
  see notes/cloud-followups.md #4 before widening the list.

TWO PERMISSIONS, TWO LAYERS
  browser user --[iap.httpsResourceAccessor]--> IAP --[run.invoker]--> service

  iap_access.sh     roles/iap.httpsResourceAccessor, on the IAP resource.
                    What a PERSON needs. This is the one you will use.
  invoker_access.sh roles/run.invoker, on the Cloud Run service. Held by IAP's
                    own service agent so IAP can call the app on a user's
                    behalf. Granted automatically; people do not need it.

  The two are separate resources, which is why the commands differ — see the
  header of each script.

PROGRAMMATIC ACCESS
  Not currently set up. With IAP enabled, a plain Cloud Run identity token
  (`gcloud auth print-identity-token`) is rejected with 401, and
  `gcloud run services proxy` no longer reaches the app either — IAP intercepts
  both. A script or CI job would need an OIDC token minted for IAP's OAuth
  client ID as its audience, plus its service account on the iap_access.sh
  allowlist.

Test the container locally before deploying (Cloud Run injects PORT):
  docker build -t gtm-verifier .
  docker run --rm -e PORT=8080 -p 8080:8080 gtm-verifier   # http://localhost:8080

The deployed service is deliberately single-tenant per instance and keeps
results in process memory. Read notes/cloud-followups.md before changing any
flag in deploy.sh — several of them stand in for unfixed bugs.


NOTES
-----
- Events pushed by onclick handlers right before a page navigation ARE
  captured (persistent dataLayer log in core.py survives same-origin
  navigations). Cross-origin hops start a fresh log.
- Exit code is non-zero if any non-INFO check fails, so runs can gate CI.
- Known Palm View site gaps (expected FAILs, listed in palm_view_config.yaml):
  no select_item on product tiles, no customer_type on init, no contact
  form events.
