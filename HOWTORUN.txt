HOW TO RUN AUDITS LOCALLY
================================================================================

SETUP (first time only)
------------------------
cd ~/Documents/assembly_code/website_audit_tool
source venv/bin/activate
cd gtm_verifier


TWO MODES
---------
1) FOREIGN SITE (prospect / cold audit) — no config file needed at all:
     python run.py --url https://prospect.com
   Runs the six site-agnostic audits: analytics_audit, consent_audit,
   network_audit, tag_inventory, seo, security_headers.

2) CLIENT SITE (we're under the hood) — YAML config with journeys:
     python run.py                          # config.yaml (Palm View test ground)
     python run.py --config client.yaml     # a specific client
   Runs the six audits PLUS every journey defined in the config's
   journeys: section, and verifies the expected GTM/GA4 IDs are live.

Useful flags:
  python run.py --list                     # show available audits + configured journeys
  python run.py shop cart                  # run specific audits/journeys only
  python run.py --export report.pptx       # PowerPoint instead of terminal
  python run.py --url https://staging.client.com --config client.yaml
                                           # client journeys against another env
  HEADLESS=1 python run.py ...             # no visible Chrome window


ONBOARDING A NEW CLIENT (no code changes, ever)
-----------------------------------------------
1. cp config.example.yaml client.yaml
2. Set site.base_url and (if known) tags.gtm_id / tags.ga4_id.
3. Set selectors.consent.accept_button only if the common-CMP auto-detection
   misses their banner.
4. Write journeys: for the flows that matter. Each journey is steps
   (goto / click / type / select_index / accept_consent / mark) plus
   expect blocks naming the dataLayer event, required fields
   (dot-notation), and optional regex patterns.
   Selector how-to: DevTools -> right-click element -> Copy -> Copy selector.
5. python run.py --config client.yaml

The full step/expect schema is documented in config.example.yaml and at the
top of journeys.py. palm_view_config.yaml is a complete worked example.


WEB FRONT END
-------------
flask --app webapp.app run          (from gtm_verifier/, HEADLESS=1 optional)
Open http://localhost:5000. Enter a URL for the public/authorized audits;
upload a client config YAML to also run its journeys and verify tag IDs.


DEPLOYED WEB APP (Cloud Run)
----------------------------
The web front end also runs in GCP, so the team can audit without a local venv:
project project-atlas-audit, region europe-west2, service gtm-verifier.
Open the service URL and sign in with Google; only allowlisted addresses get in.

Ship a new revision (Cloud Build builds the Dockerfile; no local Docker needed):
  ./deploy.sh

Tail logs:
  gcloud run services logs read gtm-verifier \
      --project project-atlas-audit --region europe-west2


ADDING A USER
  ./users.sh add someone@example.com [more@example.com ...]
  ./users.sh list
  ./users.sh remove someone@example.com

  Any Google account works - gmail.com, a client's domain, anything.
  ./users.sh updates ALLOWED_USERS on the running service (a new revision, no
  rebuild, ~30s). Keep deploy.sh's ALLOWED_USERS default in sync or the next
  full deploy reverts it.

  Everyone on the list can drive a real browser at any PUBLIC url from inside
  GCP. Private/loopback/link-local targets are refused by net_guard.py, but
  read notes/cloud-followups.md #4 before adding people outside the team.


HOW SIGN-IN WORKS (and why it is not IAP)
  Google OAuth in the app itself (gtm_verifier/webapp/auth.py): Google proves
  who you are, ALLOWED_USERS decides whether you may in.

  This started as Cloud Run's built-in IAP, which was abandoned because it
  authenticates against a Google-managed OAuth client and therefore admits only
  identities inside the project's own organisation (cloud-runner.co.uk).
  Approved users on gmail.com or assemblyglobal.com were rejected no matter
  what the IAM allowlist said, and a custom OAuth client cannot be attached to
  Cloud Run's integrated IAP - gcloud accepts --oauth2-client-id only for
  app-engine and backend-services. The alternative was an external load
  balancer; app-level auth was chosen instead.

  The app REFUSES TO START if auth is neither configured nor explicitly
  disabled, so --allow-unauthenticated on the service cannot leave it open.

FIRST-TIME GCP SETUP (once per machine)
  gcloud auth login fela@cloud-runner.co.uk
  gcloud config set account fela@cloud-runner.co.uk
  gcloud config set project project-atlas-audit
  gcloud services enable run.googleapis.com cloudbuild.googleapis.com \
                         artifactregistry.googleapis.com secretmanager.googleapis.com

FIRST-TIME OAUTH SETUP (once per project, console only)
  1. APIs & Services -> OAuth consent screen -> External. Publish it, so
     sign-in is not capped at 100 manually-listed test users. Publishing
     exposes nothing: ALLOWED_USERS is what grants access.
  2. APIs & Services -> Credentials -> Create credentials -> OAuth client ID
     -> Web application. Authorised redirect URI must be EXACTLY:
        https://gtm-verifier-ugecjj4wua-nw.a.run.app/auth/callback
     Add the alias URL too if you use it:
        https://gtm-verifier-1014181982156.europe-west2.run.app/auth/callback
  3. Store the credentials (the app reads them from Secret Manager):
        printf %s 'CLIENT_ID' | gcloud secrets create gtm-verifier-oauth-client-id \
            --project project-atlas-audit --replication-policy=automatic --data-file=-
        printf %s 'CLIENT_SECRET' | gcloud secrets create gtm-verifier-oauth-client-secret \
            --project project-atlas-audit --replication-policy=automatic --data-file=-
     Then let the runtime service account read them:
        for s in gtm-verifier-oauth-client-id gtm-verifier-oauth-client-secret \
                 gtm-verifier-flask-key; do
          gcloud secrets add-iam-policy-binding "$s" --project project-atlas-audit \
            --member='serviceAccount:1014181982156-compute@developer.gserviceaccount.com' \
            --role='roles/secretmanager.secretAccessor'
        done

  Rotating a credential: add a new secret version, then redeploy (the service
  pins :latest at deploy time, so a new version alone changes nothing).

  gtm-verifier-flask-key signs the session cookie. Replacing it signs everyone
  out; it was generated at setup and never needs to be seen.

PROGRAMMATIC ACCESS
  Not set up. The app expects an interactive Google sign-in and a session
  cookie; there is no API token path. A CI job would need a service account
  flow adding to webapp/auth.py.

RUN THE CONTAINER LOCALLY (Cloud Run injects PORT)
  docker build -t gtm-verifier .
  docker run --rm -e PORT=8080 -e AUTH_DISABLED=1 -p 8080:8080 gtm-verifier
  # http://localhost:8080 - AUTH_DISABLED skips sign-in. LOCAL USE ONLY.

  To audit a local/staging site, the SSRF guard needs the same opt-out:
  ALLOW_PRIVATE_TARGETS=1 (env var, both CLI and web app). Without it, private,
  loopback and link-local targets are refused.

The deployed service is deliberately single-tenant per instance and keeps
results in process memory. Read notes/cloud-followups.md before changing any
flag in deploy.sh - several of them stand in for unfixed bugs.

NOTES
-----
- Events pushed by onclick handlers right before a page navigation ARE
  captured (persistent dataLayer log in core.py survives same-origin
  navigations). Cross-origin hops start a fresh log.
- Exit code is non-zero if any non-INFO check fails, so runs can gate CI.
- Known Palm View site gaps (expected FAILs, listed in palm_view_config.yaml):
  no select_item on product tiles, no customer_type on init, no contact
  form events.
